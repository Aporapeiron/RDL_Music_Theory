# 検証記録：Bから候補空間が生成される条件

*対象：`B + M_B + Γ → C(B, M_B;Γ)` の音楽側固有部分*
*状態：DRAFT v0.1 / 正式Module化前の実験*
*実装：`10_検証/boundary_candidate_generation.py`*

---

## ■ 0. 検証目的

前段の純粋候補集合実験では、候補集合がすでに与えられている状態から、制約を適用した。

```text
C → R → C'
```

次に必要なのは、その手前である。

```text
B
↓
？
↓
C(B)
```

この実験では、C majorを最初から7和音の集合として入力しない。
`B`と、候補を生成する規則を分け、何が候補空間を立ち上げているかを確認する。

---

## ■ 1. 二つの段階を分離する

候補生成と、生成後の候補絞り込みを次の二段階に分ける。

```text
B + M_B + Γ
      ↓
   C(B, M_B; Γ)
      ↓ R
      C'
```

ここで、

```text
B      = 参照境界・座標系
M_B    = Bの内部で保持されている関係構造
Γ      = 候補を作るための生成規則
C(B, M_B;Γ) = B・M_BとΓから生成された候補空間
R      = 生成後の候補へ適用する制約
C'     = 制約後の候補集合
```

`C(B)`という表記は、`M_B`と生成規則を省略した短縮表記である。
生成規則の依存性が未回収な段階では、`C(B, M_B;Γ)`と書く方が安全である。

---

## ■ 2. Bを分解する

今回のC major実験では、簡略化した境界パッケージを次のように置く。

```text
B_Cmaj:
  tuning = 12TET
  tonic = C
  scale = {C, D, E, F, G, A, B}
```

ただし、これは一つの圧縮表記である。より分解すると、

```text
B:
  pitch_universe = {C, C#, D, D#, E, F, F#, G, G#, A, A#, B}
  reference_point = C

M_B:
  preserved_pitch_inventory = {C, D, E, F, G, A, B}
```

となる。

この実験では、`scale`を候補集合そのものとは扱わない。
`scale`は、候補を生成するときに参照される境界内の関係である。

実装上は、`B`と`M_B`を分けて保持する。
今回の実験では、`M_B`をC majorの音高インベントリに固定し、生成規則`Γ`を変える。
したがって、`M_B`自体を変えた場合の候補空間の変化は、まだ検証していない。

---

## ■ 3. Γ：候補生成規則

候補生成規則は、少なくとも次の選択を含む。

```text
root_source
  根音を音高全体から選ぶか、scale内から選ぶか

qualities
  どの和音種を候補として許すか

closure
  和音の構成音をscale内に閉じるか
```

今回の主規則を、次のように置く。

```text
Γ_diatonic_triad:
  root_source = M_B.pitch_inventory
  qualities = {major, minor, diminished}
  closure = all chord tones ∈ scale
```

これは「C majorだから7和音」と宣言しているのではない。

```text
scale内の根音を選ぶ
+ 3種類の三和音形を試す
+ 構成音がscale内に収まるものを残す
```

という生成手順を指定している。

---

## ■ 4. C(B, M_B; Γ)の生成

`Γ_diatonic_triad`を適用すると、候補は次の手順で生成される。

```text
scale内の根音 7個
× major / minor / diminished
↓
21個の仮候補
↓
構成音がscale内に収まるものだけを保持
↓
7個の候補
```

結果は次の通りである。

| 根音 | 残る和音種 | 候補 |
|---|---|---|
| C | major | I / C |
| D | minor | ii / Dm |
| E | minor | iii / Em |
| F | major | IV / F |
| G | major | V / G |
| A | minor | vi / Am |
| B | diminished | vii° / Bdim |

したがって、

```text
C(B_Cmaj, M_B; Γ_diatonic_triad)
= {I, ii, iii, IV, V, vi, vii°}
```

となる。

重要なのは、7候補が`B_Cmaj`から直接読み出されたのではなく、
`B`・`M_B`に生成規則`Γ`を接続した結果として得られたことである。

---

## ■ 5. 同じBから異なる候補空間が生成される

`B_Cmaj`を変えず、`Γ`だけを変える。

| 生成規則 | 根音 | 和音種 | 閉包条件 | 候補数 |
|---|---|---|---|---:|
| `Γ_diatonic_triad` | scale内 | 3種 | scale内 | 7 |
| `Γ_all_triads` | 12音全体 | 3種 | なし | 36 |
| `Γ_major_diatonic` | scale内 | majorのみ | scale内 | 3 |

この結果は、

```text
B・M_B = 同じ
Γ = 異なる
↓
C(B, M_B;Γ) = 異なる
```

ことを示す。

したがって、候補空間を説明する際に、

```text
C(B)はBだけから決まる
```

と置くのは早い。
少なくとも現段階では、

```text
C(B, M_B;Γ)
```

と書き、生成規則を未回収の依存変数として残す必要がある。

---

## ■ 6. Γを与えない場合

`B_Cmaj`と`M_B`を与え、生成規則を指定しない場合、候補集合を空集合とは判定しない。

```text
B_Cmaj + M_B + Γなし
↓
候補生成規則が不足
↓
generation_status = under_specified
```

これは、候補が存在しないこととは異なる。

```text
under_specified
  何を候補として作るかが未指定

no_candidate
  生成規則と候補空間が指定された後、結果が0個
```

前者は生成前の不足であり、後者は生成後または制約適用後の結果である。
両者を同じ`no_candidate`として扱わない。

---

## ■ 7. 今回確認できた構造

今回の最小実験で確認できるのは、次の範囲である。

```text
BとM_Bだけでは、候補空間の生成規則が不足する場合がある。
BとM_BにΓを接続すると、C(B, M_B;Γ)を生成できる。
同じB・M_Bでも、Γが変われば候補空間は変わる。
C(B, M_B;Γ)の生成と、C → R → C'の制約処理は別段階である。
生成前のunder_specifiedと、生成後のno_candidateは異なる。
```

また、既存のC major実験で使われていた7候補は、
候補空間として直接与えられたものではなく、
今回の`Γ_diatonic_triad`を暗黙に採用した結果と読み直せる。

---

## ■ 8. 今回まだ確定していないもの

この実験は、`Γ`の存在を分離しただけであり、Γの由来までは説明しない。

未回収なのは、次の部分である。

```text
Γはどこから来るのか
何を保存したいときに、どのΓが選ばれるのか
ΓはM_Bから抽出されるのか、外部の慣習として与えられるのか
M_B自体は何を契機に成立し、いつ変わるのか
反復や履歴によってΓは変わるのか
候補空間の外側に残るξを、いつ別のΓやBへ接続するのか
```

特に、`Γ_diatonic_triad`は西洋調性・12平均律・三和音という既存音楽体系を使った実験用規則である。
この規則自体をRDL音楽_Coreへ追加しない。

---

## ■ 9. 暫定結論

```text
B ≠ C(B)
B + M_B + Γ → C(B, M_B;Γ)
C(B, M_B;Γ) → R → C'
```

現段階では、次の記法が最も誤読が少ない。

```text
B + M_B
↓ Γ
C(B, M_B;Γ)
↓ R
C'
```

この実験は、C majorの和声理論を確定するものではない。
また、`Γ`をCoreの新しい固定要素として追加するものでもない。
次に調べるべきなのは、音楽的な目的や履歴が、どのように生成規則`Γ`の選択へ作用するかである。
