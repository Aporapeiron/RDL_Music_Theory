# 検証記録：リズム境界変更による候補空間再構成

*対象：25の単純リズム候補Module*  
*状態：DRAFT v0.1 / structural transition実効性の最小検証*  
*実装：`10_検証/rhythm_boundary_reconstruction.py`*

---

## ■ 0. 検証目的

25で記録した`reopen_grid_boundary`を、25で使った候補語彙と制約器を再利用する
26専用の境界依存候補生成器へ接続し、

```text
grid_open=False
  ↓ structural transition
grid_open=True
  ↓ candidate_space再生成
候補空間が変化
```

が成立するかを、リズムModule内だけで検証する。03の既存`candidate_space`は
静的な閉じた候補集合の実験として変更しない。

これは共通Adapterの実装ではない。24・25で確定したイベント境界を、次の候補生成条件へ接続したときの動態を確認する小実験である。

## ■ 1. 境界変更前後

閉じた境界では、候補は表拍・裏拍だけである。

```text
grid_open=False
候補 = 表拍 / 裏拍
```

開いた境界では、実験上の新しい候補として休符を追加する。

```text
grid_open=True
候補 = 表拍 / 裏拍 / 休符
```

休符を追加すること自体は、音楽一般の規則として主張しない。この実験で定義した候補生成条件の変更である。

## ■ 2. 検証経路

```text
R1
  → target=休符を評価
  → 閉じた候補空間では空候補を観測
  → reopen_grid_boundary
  → R2
  → 26専用の動的候補生成器で開いた候補空間を再生成
  → target=休符を再評価
  → 休符候補を得る
```

境界変更前の`target_rest`は`no_candidate`として観測される。構造遷移後に同じ条件を再評価すると、候補空間が変化して`休符`が一候補として得られる。

## ■ 3. 実測結果

```text
変更前
  candidates = ()
  status     = no_candidate

構造遷移
  operation_kind       = reopen_grid_boundary
  source_grid_open     = False
  resulting_grid_open  = True

変更後
  candidates = (休符,)
  status     = locally_resolved
```

したがって、この実験では`structural_transition`が単なるイベントラベルではなく、次の候補生成条件を変更し、再生成された候補の観測結果へ影響することを確認した。

## ■ 4. 境界

今回確認したのは、リズムModule内における次の接続だけである。

```text
structural transition
  → Module状態の変更
  → 26専用のdynamic_candidate_spaceの再生成
  → 同一条件の再観測
```

まだ共通化していないものは次のとおりである。

- 共通`projector`
- 共通`change_axes`
- Module横断の状態意味
- 共通controller
- 履歴間の因果・時系列順

また、候補へ休符を追加する境界定義は、この最小実験に固有である。音程Moduleとの間で同じ候補生成規則が成立したことは意味しない。

## ■ 5. 暫定結論

25で未検証だった、

```text
reopen_grid_boundary
  → 候補生成条件の変更
  → 候補空間の再構成
```

が、リズムModule内で成立した。ここで再利用したのは25の候補語彙と制約器であり、
03の静的`candidate_space`自体は変更していない。

よって、現時点では`structural_transition`を「構造遷移の記録」だけでなく、「後続の候補生成条件を変更し得るModule側イベント」として扱う根拠が、リズムModuleで得られた。音程Moduleでは今回と同じ候補再構成の接続を検証していないため、両Moduleで同一の候補再構成規則が確認されたわけではない。

共通Adapterの完成、共通controller、因果順の再構成へは拡張しない。
