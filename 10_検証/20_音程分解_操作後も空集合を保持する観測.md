# 検証記録：音程分解・操作後も空集合を保持する観測

*対象：操作後も候補が空のまま残る場合を、選択失敗・状態遷移・未解決ξから分離して記録する最小実験*
*状態：DRAFT v0.1 / 音程分解Module候補*
*実装：`10_検証/empty_action_observation.py`*

---

## ■ 0. 検証目的

19では、現在状態へ操作を適用し、候補を再生成してから実際の`change_axes`を計算した。
ただし、`observe_action()`は再生成後に`selected is None`となると例外で停止していた。

```text
操作を試す
  ↓
候補を再生成
  ↓
まだempty
  ↓
ValueErrorで観測が消える  ← 19までの破断
```

20では、候補が空のままでも操作観測を保持する。
選択された次状態の履歴と、操作を試した結果の観測履歴を分離し、さらに
`empty`という既知の状態診断と、復旧方針が未定義な`ξ`を分けて記録する。

これは、空集合を直ちに失敗・例外・B引き直しの根拠へ変換しないための最小検証である。

---

## ■ 1. 観測と遷移の分離

19から、`ActionObservation`は`selected=None`を保持できるようにした。
空候補の場合、`BranchEvaluation`は作らない。これは採用比較のための評価対象と、
候補が存在しないという診断を混同しないためである。

```text
ActionObservation
├─ operation_status
├─ change_axes
└─ ReexplorationObservation
   ├─ status
   ├─ failure_stage
   ├─ failure_reason
   └─ selected = None

BranchEvaluation
└─ selected候補がある操作だけを対象に作る
```

`operation_status = applied`でも、候補再生成の結果が`empty`になることはある。
これは「操作が状態条件を変えたか」と「候補が選択可能になったか」が別の軸だからである。

---

## ■ 2. 空集合を生じる操作

19の三操作そのものを音楽一般の規則へ拡張するのではなく、20では検証用に
`B_tighten`を一つ注入する。

```text
S0
  B = voice A: candidate octave (4), range E♯4–A♯4
  Γ = pitch(voice A) < pitch(voice B)
  target = (3, 1)
  candidate = A♯4 / F♯4
  status = no_admissible_candidate

B_tighten
  B = voice A: candidate octave (4), range E♯4–G♯4
  Γ と target は維持
  candidate = A♯4 が範囲外
  status = constraint_no_candidate
```

`B_tighten`は境界を変更しているため、

```text
operation_status = applied
change_axes = boundary_changed
```

となる。一方、候補は範囲投影で消えるため、

```text
selected = None
failure_stage = B_range_projection
```

となる。

ここでは、操作が実行されたことと、候補が戻ったことを同一視しない。

---

## ■ 3. 空状態の保持

`advance_empty_observation()`は、選択された具体音を持たないため、通常の
`DynamicStateTransition`を追加しない。その代わり、次の条件を保持した状態を作る。

```text
state_t
  ↓ B_tighten
state_t+1[empty]
  ├─ last_realized_pairは直前に実現したペアを保持
  ├─ Bは操作後の境界へ更新
  ├─ selected pairは存在しない
  ├─ realized_transition_historyは増えない
  └─ observation historyへ操作結果を追加
```

`last_realized_pair`を残すのは、具体音が選ばれなかったことと、次の移動基準が消滅することを
同一視しないためである。ただしこれは現在の`B`で有効な`current valid pair`を意味しない。
この実験では、`B_tighten`後の`B`が`A♯4`を許容しなくても、直前に実現した
`A♯4–F♯4`を移動基準として保持する。

したがって、`last_realized_pair`は「空状態での現在位置」を確定する名前ではなく、
最後に具体音として実現したペアを基準点として残す、今回の最小実験における保持方法である。

`realized_transition_history`が増えていなくても、直前の操作で実際に生じた
`change_axes`は状態へ保持される。したがってcontrollerは「履歴なし」へ戻らず、
`B_tighten`による`boundary_changed`を次の方針選択へ渡せる。

ここで`realized_transition_history`が増えないのは、状態条件が変化していないという意味ではない。
この履歴が記録する対象を「選択された具体音を伴う採用遷移」に限定しているためである。
操作観測そのものは、別の`observation_history`へ記録する。

その後の`observe_actions()`では、同じ空状態から各操作を再評価する。
空のまま残った操作も、`ActionObservation`と観測履歴へ残るが、
`BranchEvaluation`を持たないため採用比較からは除外される。

## ■ 4. 観測された結果

```text
S0
  → B_tighten / applied
  → constraint_no_candidate
  → S1_empty

S1_empty
  ├─ B_change / applied
  │  → selected candidate
  │
  ├─ Γ_change / applied
  │  → constraint_no_candidate
  │  → 観測履歴には残るが採用比較から除外
  │
  └─ upstream_target_change / applied
     → selected candidate
     → 採用比較へ入る
```

三操作はいずれも観測されるが、実際に採用されるのは方針による比較後の
`upstream_target_change`である。したがって、採用結果の列と操作観測の列を分けて読む必要がある。

この結果から、同じ操作集合に対しても、

```text
操作状態の変更
候補が存在するか
候補を比較できるか
次状態として採用されたか
```

を別々に記録する必要がある。

---

## ■ 5. `empty`と未解決ξ

今回の`empty`は、現在の`B`・`Γ`・targetのもとで候補が存在しないという既知の観測である。
`failure_stage`と`failure_reason`によって、範囲投影で消えたことを記録できる。

一方、次の事項は今回の観測だけからは決まらない。

```text
どの復旧操作を次に採用するか
空状態での試行を何回まで続けるか
同じ層のB変更と上流target変更をどう比較するか
empty状態でlast_realized_pairをどの範囲まで移動基準とみなすか
```

これらを`ξ`として残す。したがって、

```text
empty = 現在条件から得られた既知の診断
ξ     = 次の扱い・比較・境界が未定義な部分
```

であり、同じ欄へ押し込めない。

---

## ■ 6. この実験から言えること

```text
1. 操作後も候補が空のままになることは、例外ではなく観測可能な結果である。
2. operation_statusと候補のstatusは別軸で保持できる。
3. 空観測は選択評価へ入れず、観測履歴には残せる。
4. 空観測を記録しても、選択された遷移履歴へ空の具体音を捏造せずに済む。
5. 同じ空状態から、別操作による候補復帰を再探索できる。
6. emptyの診断と、次の復旧方針が未定義なξを分離できる。
```

## ■ 7. Coreとの境界

20で追加したのは、空候補を捨てずに観測するための検証構造である。

```text
Core
  観測・状態差分・遷移履歴を分離して記録する共通文法

20 Module
  B_tightenという検証用操作
  12平均律長音階の声域境界
  B_range_projectionでのempty診断
  空観測を採用比較から除外する接続
```

`B_tighten`、voice range、`Γ_ordering`、target degreeは、引き続きこの音程分解
Moduleの`M_B`と`Γ`に留める。Coreへ昇格させない。

---

## ■ 8. 未解決ξ

```text
空状態からの復旧方針をcontrollerがどう選ぶか
空状態でのlast_realized_pairの意味をどこまで保持するか
操作後もemptyが続く場合の打ち切り条件
複数のfailure_stageを持つ複合emptyの記録
empty状態から別の空状態へ移る場合の状態同一性
```

今回の実装では、これらを決めずに、操作観測を消失させないところまでを検証した。
