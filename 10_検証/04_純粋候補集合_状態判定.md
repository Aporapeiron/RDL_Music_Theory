# 検証記録：純粋候補集合の状態判定

*対象：音楽語彙を使わない候補集合と制約*  
*状態：現範囲の検証完了 / 一般実験として保留*
*実装：`10_検証/generic_candidate_operations.py`*

---

## ■ 0. 目的

C majorと単純リズムで現れた「制約適用後の候補数による状態判定」を、音高・和声・拍子・リズムを使わない最小入力で確認する。

この実験の対象は音楽理論ではなく、既に与えられた候補集合への制約適用である。したがって、ここから音楽固有の法則やRDL Coreの新原理は導かない。

---

## ■ 1. 純粋候補集合

候補は意味を持たないラベルとして、直接入力する。

```text
C = {A, B, C}
```

この実験では、RDLの境界 `B` を候補集合の宣言として置かない。

```text
B → 候補空間生成 → C(B)
```

という生成過程は、今回の検証対象から外す。ここで扱うのは、独立した入力 `C` がすでに与えられた後の処理だけである。

---

## ■ 2. 制約

現在候補を `A` とし、現在候補を除外する制約と、必要に応じて目標条件を適用する。

```text
R1(x) := x ≠ current
R2(x) := x = target
```

目標条件を使わない場合は `R1` のみ、目標条件を指定する場合は `R1` と `R2` を適用する。

---

## ■ 3. 制約後集合

制約後の候補集合を、次で定義する。

```text
C' = {x ∈ C | R1(x) ∧ R2(x)}
```

目標条件を指定しない場合は、`R2` を恒真条件として扱う。

### 現在候補だけを変更する場合

```text
current = A
target = 未指定
C' = {B, C}
```

### 目標条件を追加する場合

```text
current = A
target = C
C' = {C}
```

### 条件が候補空間と衝突する場合

```text
current = A
target = X
C' = ∅
```

`X` は `C` に含まれないため、解なしになる。

---

## ■ 4. 局所状態

状態は、目標条件の有無ではなく、制約後集合の要素数で判定する。

```text
|C'| = 0  → no_candidate
|C'| = 1  → locally_resolved
|C'| > 1  → underdetermined
```

ここでの `locally_resolved` は、入力された `C` と適用した制約の内部で一候補に絞られたことを表す。候補空間の外側に別の可能性がないことや、音楽的に唯一正しいことは意味しない。

`no_candidate` も直ちに破断を意味しない。現在の `C` と制約の組み合わせで解がないため、候補空間を広げる、制約を緩める、境界を引き直す、といった次の診断へ進む状態である。

---

## ■ 5. これは何ではないか

今回確認したのは、次の一般的な構造である。

```text
C
↓ 制約 R
C'
↓ |C'|
局所状態
```

これは、音楽理論の法則ではない。また、RDL音楽固有の原理でもない。候補絞り込みと候補数による状態分類という、既知の一般機構として扱う。

3つの実験で同じコード設計が再現したことだけを根拠に、Coreへ新しい原理を追加しない。

---

## ■ 6. RDLへの接続候補

RDL音楽側で未検証なのは、候補集合への制約適用ではなく、境界から候補空間が成立する過程である。

```text
B
↓
候補空間生成
↓
C(B)
↓ 制約 R
C'
```

ここでは、`B` と `C(B)` を同一視しない。一般側の `C → R → C'` と、RDL側の `B → C(B)` を分けて記述する。

---

この文書では、これらを数値化せず、一般側の候補集合実験もここで増やさない。次の検証は、音楽において `B` を変えると `C(B)` がどう変わるかへ戻す。

---

## 暫定結論

純粋候補集合によって、次の一般機構を確認した。

```text
C → 制約 R → C'
|C'| = 0  → no_candidate
|C'| = 1  → locally_resolved
|C'| > 1  → underdetermined
```

これは現範囲で検証を閉じ、一般的な候補制約の道具として分離する。Core・正式Moduleには追加しない。
