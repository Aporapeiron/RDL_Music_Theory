# 検証記録：音程分解・状態からの再探索枝再生成

*対象：B・Γ・targetを含む現在状態へ操作候補を適用し、候補を再生成する最小動態*
*状態：DRAFT v0.2 / 音程分解Module候補*
*実装：`10_検証/state_rebased_reexploration.py`*

---

## ■ 0. 検証目的

18では、履歴から次の`SearchPolicy`を選ぶ接続を確認した。ただし、16の
初期seedから一度だけ生成した固定枝を再利用していたため、枝テンプレートの
`change_axes`と現在状態から実際に起きた変化がずれる可能性が残った。

19では、枝を固定された結果ではなく、現在状態へ適用する操作候補として扱う。

```text
state_t
  ↓ action candidateを適用
B_t+1 / Γ_t+1 / target_t+1
  ↓ 候補を再生成
C(state_t+1)
  ↓ state_tとの差分を計算
actual change_axes
  ↓ 履歴へ保存
state_t+1
```

これは音楽一般の再探索規則ではなく、16〜18の構造を接続する検証用の
小さな動態である。Coreへ音楽固有のB・Γ・targetを追加しない。

---

## ■ 1. 現在状態の構造

19では、具体音の結果だけでなく、次の生成条件そのものを状態へ保持する。

```text
DynamicSearchState
├─ context
├─ last_realized_pair（voice A / voice Bの最後に実現した音高）
├─ voice_A / voice_Bのtarget degree
├─ voice_A / voice_BのRealizationBoundary
│   ├─ candidate_octaves
│   └─ voice_range
├─ pitch_ordering_rule
└─ realized_transition_history
```

`last_realized_pair`はS0ではseedの開始音`A♯4–F♯4`で初期化し、採用候補が決まるたびに
その候補へ更新する。これは現在の`B`で有効なペアを保証する名前ではなく、次の
具体音選択に使う移動基準である。`selected_pair`は一回の観測結果であり、次状態の
基準点を別に保持する二重情報にはしない。

ここで、

```text
B       = candidate_octaves + voice_range
Γ       = pitch_ordering_rule
target  = voiceごとのtarget degree
```

として、次状態の候補生成に必要な値を明示する。

`selected_pair`だけを持つ18の状態では、現在のtargetやBがすでに変更済みかを
判定できなかった。19では適用前後の状態を比較できるため、枝名から性質を
復元する必要がない。

---

## ■ 2. 操作候補

三つの候補は、初期seedの結果を保存したものではなく、現在状態へ適用する操作である。

| 操作候補 | 適用する変更 | 再実行される層 |
|---|---|---|
| `B_change` | voice Aの候補オクターブ・声域を開く | 実現層 |
| `Γ_change` | crossed voice pitchesを許容する | 実現層 |
| `upstream_target_change` | voice Aのtarget degreeを`3 → 7`へ置き換える | 上流target層→実現層 |

各操作を現在状態へ適用した後、16の`observe_request()`をその状態から再実行する。
したがって、同じ操作名でも、適用時点のB・Γ・targetによって候補集合と選択結果が変わりうる。

---

## ■ 3. 実際の変更軸

枝名や操作名を変更軸へ変換しない。
状態`state_t`と適用後の`state_t+1`を比較し、次を計算する。

```text
boundary_changed
  = B_t と B_t+1 が異なるか

relation_changed
  = Γ_t と Γ_t+1 が異なるか

upstream_target_changed
  = target_t と target_t+1 が異なるか
```

そのため、すでにtarget degreeが7の状態へ同じtarget操作を適用した場合は、

```text
operation_status = no_effect
change_axes = {
  boundary_changed: false,
  relation_changed: false,
  upstream_target_changed: false
}
```

となる。`no_effect`は観測結果として保持するが、今回の採用比較からは除外する。
既適用操作を「再びtargetを変更した」と履歴へ記録しないためである。

---

## ■ 4. 状態からの再生成

### S0：初期空集合

```text
target = (3, 1)
B      = voice A: octave (4), range E♯4–A♯4
         voice B: octave (4), range F♯4–F♯4
Γ      = strict_voice_a_pitch_lt_voice_b_pitch
```

現在の候補は`A♯4 / F♯4`で、厳密な実音高順序により空集合になる。

ここから操作候補を再生成すると、初回の評価は次の通りである。

| 操作 | status | 実際の変更 | 選択候補 |
|---|---|---|---|
| `B_change` | `applied` | `boundary_changed` | `A♯3–F♯4` |
| `Γ_change` | `applied` | `relation_changed` | `A♯4–F♯4` |
| `upstream_target_change` | `applied` | `upstream_target_changed` | `E♯4–F♯4` |

`target_continuity_then_relation`により、ここでは`B_change`が採用される。

### S1：B変更後

S1では、Bがすでに開いている。
それでも三つの操作候補を再実行し、S1のBから候補を生成する。

```text
S1
  → B_change                   → no_effect
  → Γ_change                   → relation_changed
  → upstream_target_change     → target degree 7を適用
```

このとき`upstream_target_change`のvoice A候補は、S0の`E♯4`だけではなく、
S1の広がったBから`E♯3 / E♯4`として再生成される。さらに`Γ_select`の開始点も
S0の`A♯4`ではなく、S1の`last_realized_pair`にある`A♯3`である。

```text
A♯3 → E♯3 = 5半音
A♯3 → E♯4 = 7半音
```

したがって選択結果は`E♯3–F♯4`となる。候補集合だけでなく、具体音選択の基準も
S1から再基準化されている。

`strict_relation_then_boundary`は、no_effectの`B_change`を採用比較から除外し、
有効な厳密順序維持候補である`upstream_target_change`を採用する。

### S2：target変更後

S2ではtarget degreeがすでに7で、`last_realized_pair`は`E♯3–F♯4`である。
したがって、同じtarget操作を再度適用しても、

```text
upstream_target_change
  → operation_status = no_effect
  → upstream_target_changed = false
```

として検出される。

このとき、`minimum_immediate_motion`の有効候補は`Γ_change`であり、
S2からは次の状態へ関係規則だけが変化する。

```text
S2
  → Γ_change
  → relation_changed = true
  → S3
```

## ■ 5. 観測された履歴

```text
S0_empty
  ↓ target_continuity_then_relation
  → B_change / applied
  → S1: A♯3–F♯4

S1
  ↓ strict_relation_then_boundary
  → upstream_target_change / applied
  → S2: E♯3–F♯4

S2
  ↓ minimum_immediate_motion
  → Γ_change / applied
  → S3: E♯3–F♯4, relaxed ordering
```

履歴へ保存される実際の変更軸は次の通りである。

| 遷移 | 採用操作 | operation status | 実際の`change_axes` |
|---|---|---|---|
| `S0 → S1` | `B_change` | `applied` | `boundary_changed` |
| `S1 → S2` | `upstream_target_change` | `applied` | `upstream_target_changed` |
| `S2 → S3` | `Γ_change` | `applied` | `relation_changed` |

一方、S2で観測された未採用のtarget操作は、

```text
no_effect
≠ upstream_target_changed
```

として残る。ここで、枝テンプレートの性質と現在状態から実際に起きた変化が
分離された。

---

## ■ 6. この実験から言えること

```text
1. 次状態へ影響するB・Γ・targetと、具体音選択の基準となる現在音高は状態として必要である。
2. 枝を操作として保持すれば、現在状態ごとに候補を再生成できる。
3. 実際のchange_axesは、操作名ではなく状態差分から計算できる。
4. 同じ操作を再適用しても、no_effectとして検出できる。
5. no_effectと既知のemptyは別の観測である。
6. 候補再生成、方針選択、操作適用、履歴保存を別層に保持できる。
7. `last_realized_pair`を遷移ごとに更新すれば、`Γ_select`の移動基準も`state_t`へ再基準化できる。
```

18までの接続は、19で次の形へ更新された。

```text
現在状態
  ↓
操作候補を適用
  ↓
B / Γ / targetを更新
  ↓
last_realized_pairを基準に候補再生成・選択
  ↓
採用候補をstate_t+1のlast_realized_pairへ更新
  ↓
状態差分からactual change_axes
  ↓
履歴
  ↓
次回方針
```

## ■ 7. 未解決ξ

```text
no_effect操作を候補集合へ残す条件
no_effectを採用比較から除外する規則の起源
同一操作が別のtarget値を選べる場合の表現
B・Γ・targetの複合変更
状態履歴からB・Γ・target・last_realized_pairを再構成する範囲
状態の同一性をlast_realized_pair以外に何で判定するか
方針controller自体の更新
候補が再生成後もemptyになる場合の観測保持と復帰
```

今回の`no_effect`除外は、既適用操作の二重記録を防ぐために注入した
検証用条件であり、一般的な探索原理としては扱わない。

## ■ 8. Coreとの境界

19で追加したのは、Coreの新しい音楽固有状態ではない。

```text
Core
  状態差分・遷移・履歴を記述する共通文法

19 Module
  12TET長音階のtarget degree
  voice A / voice BのRealizationBoundary
  pitch_ordering_rule
  現在状態へ適用する三つの操作
  no_effectを含む候補再生成の観測
```

12平均律、長音階、音度、声部範囲、声部順序は、この検証Moduleの`M_B`と`Γ`に
留める。Coreへ昇格させない。

## ■ 9. 実行結果

```text
S0_empty → B_change / applied → S1
S1       → upstream_target_change / applied → S2
S2       → upstream_target_change / no_effect
S2       → Γ_change / applied → S3
```

実験スクリプト内のassertで、現在状態からの候補再生成、`last_realized_pair`を基準にした
具体音選択、実際の変更軸、`no_effect`検出、履歴の変更軸列を確認する。S1からの
target変更では、初期`A♯4`基準なら`E♯4`になるところ、現在`A♯3`基準では
`E♯3`が選ばれる。
